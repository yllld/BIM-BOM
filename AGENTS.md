# Инструкция для Codex

## Назначение

Этот репозиторий содержит плагины **DWG Converter — Family Geometry** для Autodesk Revit 2021 и Revit 2025. При любых изменениях Codex должен сохранять совместимость с целевой версией Revit, не затрагивать пользовательские правки и оставлять репозиторий в проверяемом состоянии.

## Структура решения

- `FamilyConverter.Revit2021/` — основной код плагина для Revit 2021, .NET Framework 4.8 и WPF.
- `FamilyConverter.Revit2025/` — адаптация для Revit 2025 на .NET 8 (`net8.0-windows`). Проект переиспользует большую часть C#- и XAML-файлов из `FamilyConverter.Revit2021/`.
- `DWGConverter.FamilyGeometry.Installer/` — установщик версии 2021.
- `DWGConverter.FamilyGeometry.Revit2025.Installer/` — установщик версии 2025.
- `dist/` — готовые установщики для выдачи.
- `README.md` — пользовательская и техническая документация.

Изменение общего файла в `FamilyConverter.Revit2021/` может одновременно влиять на обе версии. Исключения, перечисленные в `FamilyConverter.Revit2025.csproj`, и код из `DrawingToFamily/` относятся к версии 2025 не всегда — перед изменением проверять состав проектов.

## Ветки

- `main` — стабильная основная версия для Revit 2021 и ветка GitHub по умолчанию.
- `revit-2025` — версия для Revit 2025. Общие исправления переносить сюда осознанно после проверки совместимости с .NET 8 и Revit API 2025.
- `2d-converter` — изолированная разработка команды `2D Drawing to Family` и связанных моделей, сервисов, UI и документации.

Не сливать `2d-converter` целиком в ветки версий. Общие изменения переносить отдельными проверяемыми коммитами. Не смешивать в одном коммите развитие 2D-конвертера и независимые исправления 3D-команд.

## Как вносить изменения

1. Перед началом работы прочитать задачу, `AGENTS.md`, связанные проекты и ближайший по смыслу код.
2. Выполнить `git status --short` и считать все существующие изменения собственностью пользователя. Не удалять, не откатывать и не переформатировать их без явного запроса.
3. Делать минимальное целевое изменение. Не смешивать исправление задачи с массовым рефакторингом, переименованием или форматированием несвязанных файлов.
4. Соблюдать существующие архитектуру, стиль C#/XAML и соглашения об именовании.
5. Учитывать ограничения Revit API:
   - обращаться к модели Revit только из допустимого API-контекста;
   - изменения документа выполнять внутри корректной `Transaction` или `TransactionGroup`;
   - не выполнять длительную работу и небезопасные обращения к Revit API из фонового потока;
   - корректно обрабатывать отмену пользователем и управляемые ошибки геометрии;
   - не сохранять ссылки на недействительные API-объекты между контекстами.
6. Не добавлять секреты, токены, локальные конфиги, абсолютные пользовательские пути, содержимое DWG/RFA и сгенерированные `bin/`, `obj/`, `.vs/`, логи или отчёты.
7. При добавлении файла в старый проект Revit 2021 явно включать его в соответствующий `ItemGroup` файла `.csproj`. Для связанного кода проверять, должен ли файл также попадать в сборку Revit 2025.
8. Если меняется поведение, установка, интерфейс или пользовательский сценарий, синхронно обновлять `README.md` и при необходимости manifest/installer.

## Проверка изменений

Проверять только затронутые части, но в объёме, достаточном для уверенности в результате.

Для Revit 2021:

```powershell
msbuild FamilyConverter.Revit2021.sln /p:Configuration=Release
```

Для Revit 2025:

```powershell
dotnet build FamilyConverter.Revit2025.sln -c Release
```

Для установщика Revit 2025:

```powershell
dotnet publish DWGConverter.FamilyGeometry.Revit2025.Installer\DWGConverter.FamilyGeometry.Revit2025.Installer.csproj -c Release
```

Сборки требуют установленных Revit API соответствующей версии по путям, указанным в `.csproj`. Если окружение не позволяет выполнить проверку, сообщить об этом явно и не заявлять, что сборка успешна.

Для изменений, затрагивающих общий код, по возможности собирать обе версии. Для поведения, зависящего от Revit API, дополнительно описать необходимую ручную проверку в Revit: версию приложения, тип документа, команду, входные данные и ожидаемый результат.

Перед завершением работы:

```powershell
git diff --check
git status --short
git diff --stat
```

Просмотреть итоговый diff и убедиться, что в него не попали посторонние или сгенерированные файлы.

## Коммиты

Codex не создаёт коммит без явной просьбы пользователя.

Перед коммитом:

1. Проверить текущую ветку и `git status --short`.
2. Просмотреть `git diff` и результаты выполненных проверок.
3. Сформировать коммит только из файлов текущей задачи. Не использовать бездумно `git add .` или `git add -A`, если в рабочем дереве есть чужие изменения.
4. При пересечении задачи с уже изменённым пользователем файлом добавлять только относящиеся к задаче фрагменты либо остановиться и согласовать состав коммита.
5. Не изменять предыдущие коммиты через `--amend`, rebase или force push без прямого указания.

Сообщение коммита писать на английском языке в повелительной форме, кратко и по существу, в стиле истории репозитория:

```text
Add preview controls for 2D contours
Fix Revit 2025 unit conversion
Update installer metadata
```

Один коммит должен представлять одно логическое изменение. Документацию и тесты, относящиеся к этому же изменению, включать в тот же коммит.

После коммита показать пользователю hash, сообщение, список проверок и оставшиеся незакоммиченные изменения.

## Push

Codex не выполняет `git push` без явной просьбы пользователя. Просьба «закоммить» сама по себе не означает разрешение на push.

Перед push:

1. Убедиться, что коммит создан в ожидаемой ветке и рабочее дерево имеет понятное состояние.
2. Проверить remote через `git remote -v` и ветку через `git branch --show-current`.
3. Не пушить напрямую в `main`/`master`, если пользователь явно не попросил об этом. Для разработки использовать текущую тематическую ветку.
4. Обычный push выполнять командой `git push`; для новой ветки — `git push -u origin <branch>`.
5. Никогда не использовать `--force` или `--force-with-lease` без отдельного явного разрешения и объяснения риска.

После push сообщить пользователю remote, ветку и hash отправленного коммита. Не создавать pull request, release, tag и не публиковать installer без отдельной просьбы.

## Запрещённые действия

Без явного запроса пользователя запрещено:

- откатывать или удалять существующие изменения;
- выполнять `git reset --hard`, `git clean`, `git checkout -- <file>` или эквивалентные разрушительные команды;
- менять ветку при грязном рабочем дереве, если это может затронуть текущие правки;
- коммитить секреты, локальные конфиги и сборочные артефакты;
- считать задачу проверенной только на основании визуального просмотра кода, если доступна сборка;
- публиковать изменения во внешние системы.

## Формат отчёта пользователю

В завершении кратко указать:

- что изменено;
- какие файлы являются ключевыми;
- какие проверки выполнены и с каким результатом;
- что проверить вручную в Revit;
- был ли создан коммит и выполнен push;
- какие ограничения или незакоммиченные изменения остались.
